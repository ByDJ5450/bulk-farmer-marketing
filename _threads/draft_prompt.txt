스레드 초안 8개를 생성한다. 이 중 3~5개가 승인돼 발행된다. 대화 상대는 없다. 질문하지 말고 끝까지 수행한다.

## 절차

0. **발행본 대조를 먼저 돌린다.** 초안을 쓰기 전에 한다.

   ```bash
   /usr/bin/python3 _threads/edit_diff.py
   ```

   코치는 발행한 글을 직접 고친다. **그 수정이 곧 오늘 초안의 규칙이다.**
   출력에 수정이 잡히면 오늘 8개에 그대로 반영하고, 검수 보고에 적는다.
   반복해서 같은 수정이 나오면 그건 규칙이므로 `_context/human_tone_guide.md`나
   말투 절에 추가한다 — 사람이 매번 손으로 고치게 두지 않는다.

   > 2026-08-11에 처음 돌렸더니 14건이 고쳐져 있었다. 거기서 나온 것:
   > **해시태그를 쓰지 않는다**(붙인 14건 전부 코치가 지웠다, 예외 0건),
   > **비유 대신 실제 지표 이름**("줄자는 앞으로 갔다" → "둘레는 좋아졌습니다"),
   > **막연한 총칭 대신 실제 이름**("영상" → "유튜브").
   > 그전까지 아무도 안 보고 있었고, 같은 지적이 반복되고 있었다.

   새로 발견된 것만 나온다. 한 번 본 수정은 다음부터 조용하다.
   전부 다시 보려면 `--all`.

1. `_context/threads_agent.md`, `_template/threads_template.md`, `_context/brand_guidelines.md`를 읽는다.

2. 발행 이력 대조 — 아래 두 곳을 모두 읽는다.
   - `_threads/published.md` (자동 발행 이력)
   - 발행 이력 메모리 (2026-05-04 5건, 2026-05-11 1건의 소재·훅 구조)

   **같은 주제를 다시 써도 된다. 단, 각색해야 한다.**
   하루 3~5개씩 나가므로 소재를 완전히 배제하면 금방 고갈된다.
   좋은 주제는 각도를 바꿔 다시 쓰는 편이 억지 소재를 짜내는 것보다 낫다.

   각색으로 인정되는 것 — 아래 중 **최소 두 가지**가 달라야 한다.
   - 형식 (유형 1 스토리 ↔ 2 정보 ↔ 3 질문)
   - 진입 각도 (본인 경험 ↔ 수강생 사례 ↔ 흔한 오해 반박 ↔ 숫자 제시)
   - 첫 문장 훅
   - 결론에서 남기는 행동

   각색이 아닌 것 — 이건 배제한다.
   - 문장만 바꾸고 훅·전개·결론이 같은 글
   - 같은 수치를 같은 순서로 나열한 글

   `summary` 필드에 **"[재구성] 원래 소재 → 이번 각도"** 형태로 남긴다.
   예: `[재구성] 유산소 오해 → 이번엔 수강생 사례로 진입, 결론은 주 2회 유지`

3. 조합 결정 — 8개가 서로 겹치지 않게 분산한다.
   형식: 유형 1(스토리) / 2(정보) / 3(질문)
   주제: A(오해) B(제한된 믿음) C(실수) D(노하우) E(장애물) F(사회적 증거)
   같은 형식×주제 조합을 8개 안에서 두 번 쓰지 않는다.
   주제 A~F 중 최소 5개가 등장하게 한다 — 한 주제에 몰리면 계정이 단조로워진다.
   아직 안 쓴 조합을 먼저 채우고, 남는 자리는 2번의 각색 규칙으로 채운다.

4. 초안 작성 → **카피 점검(아래 5단)** → 신뢰 검증 → JSON 저장 → 텔레그램 발송
   → **검수 보고 전송** (마지막 단계, 건너뛰지 않는다)

## 신뢰 검증 (가장 중요 — 통과 못 하면 그 초안은 버린다)

이 계정은 브랜드다. 틀린 정보 하나가 쌓아온 신뢰를 깎는다.
**애매하면 쓰지 않는다.** 8개를 채우는 것보다 6개가 정확한 게 낫다.
버린 초안은 개수를 맞추려고 억지로 메우지 않는다.

### 절대 금지

**① 지어낸 수치·연구·출처**
- "연구에 따르면", "논문에서", "전문가들은" — 실제 출처를 댈 수 없으면 쓰지 않는다
- "근육량 30% 증가", "성공률 80%" 같은 통계 — 근거 없는 숫자 금지
- 확인되지 않은 제3자 사례를 사실처럼 쓰지 않는다

**② 피트니스 사실 오류 3종**
- "운동 후 30분 이내 단백질" → "1~2시간 이내" 또는 "하루 총량 기준"
- "벌크업의 X%는 식단" → "운동(자극) + 식단(재료), 둘 다 필수"
- 벌크업 맥락에서 "칼로리를 줄이고" → "칼로리 잉여를 유지하면서"

**③ 결과 보장·과장**
- "무조건", "100%", "누구나", "반드시 성공" 금지
- "○kg 보장", "○개월이면 완성" 금지
- 수강생 사례 인용 시 "개인에 따라 결과가 다를 수 있습니다" 고지

**④ 의료·건강 주장**
- 질병 치료·예방 효과 암시 금지
- 보조제 효능 단정 금지

### 반드시 지킬 것

**본인 경험과 일반화를 구분한다.**
- (O) "저는 3개월 동안 이렇게 했더니 이랬습니다"
- (X) "3개월이면 이렇게 됩니다"

**검증 가능한 사실만 트레이너 이력으로 쓴다.**
- 확정 사실: 181cm, 55kg → 88kg, K-Classic 클래식 보디빌딩 3위
- 이 외의 수치·경력을 새로 만들어내지 않는다

**숫자를 쓸 때는 출처를 자기 경험으로 한정하거나, 원리로 설명한다.**
- (O) "체중 1kg당 단백질 1.6g 정도를 기준으로 잡습니다"  ← 통용되는 실무 기준
- (X) "연구 결과 1.6g이 최적으로 밝혀졌습니다"          ← 출처 못 대면 금지

### 각 초안마다 자기 검증 기록

JSON의 `fact_check` 필드에 아래를 남긴다.
- `claims`: 사실 주장이 들어간 문장 목록 (없으면 빈 배열)
- `basis`: 각 주장의 근거 — 아래 규칙대로 **출처를 같이 적는다**

### ⚠️ "본인 경험"은 지어낸 이야기의 구멍이다 (2026-08-11 강화)

`basis: "본인 경험"`은 저장소에서 반박할 수 없다. **그래서 그럴듯한 일화를 지어내고
"본인 경험"이라고 붙이면 그대로 통과한다.** 2026-08-11 초안 8개 중 4개가 그랬다.

| 지어낸 것 | 실제 |
|---|---|
| "많이 먹었더니 체지방만 늘었다" | 확정 이력은 **"아무리 많이 먹어도 살이 찌지 않았다"** — 정반대 |
| "정체가 아니라 회복 중이라고 말씀드렸다" | 영상에서 한 말은 **"인바디를 신경 안 쓰셨으면 좋겠다"** |
| "운동은 7가지만 합니다" (3대+OHP·풀업·딥스) | 코치 루틴이라는 근거 없음. 어디에나 있는 목록 |
| "이 몸으로는 면접에서 밀릴 거라 혼자 결론 내렸다" | 실제로는 **친구들이 "그 몸으로 승객을 보호할 수 있겠냐"고 말했다** |

**앞으로 `basis`는 넷 중 하나로만 적고, 앞의 셋은 출처를 괄호로 붙인다.**

```
"확정 이력(pDCc3pz-IrA 영상)"        영상·후기 원자료에서 문장을 찾은 것
"본인 경험(mr03Y1axP1Y 영상)"        코치가 실제로 말한 것을 찾은 것
"통용 기준"                          피트니스 일반 상식 — 본인 일화로 포장하지 않는다
"미확인"                             ← 못 찾았으면 반드시 이것
```

**출처를 못 찾으면 초안을 버리지 말고 `"미확인"`으로 적고 그대로 낸다.**
버리면 좋은 소재가 사라지고, 통과시키면 거짓이 나간다. **사용자에게 물어본다.**

`_repurpose/source/*/transcript.txt`, `_testimonials/*.md`, `_context/brand_guidelines.md`에서
먼저 찾아본다. 코치 확정 이력은 181cm · 55kg→88kg · K-Classic 3위뿐이고,
**그 밖의 개인 일화는 전부 원문을 찾아야 한다.**

### 미확인이 있으면 따로 물어본다

`basis`에 `"미확인"`이 하나라도 있는 초안은 텔레그램 본문 맨 위에 붙인다.

```
⚠️ 미확인 — 실제로 있었던 일인지 확인 부탁드립니다
   · 벤치프레스 중량 욕심으로 어깨 통증
```

그리고 초안 8건을 다 보낸 뒤, 미확인 목록만 모아 한 건으로 다시 묻는다.
**"맞으면 승인, 아니면 버림"으로 답할 수 있게 초안 번호를 같이 적는다.**

## 사진 첨부 (선택)

성훈님·재현님 케이스나 실제 측정·기록을 다루는 초안이라면 사진을 붙일 수 있다.
사진이 붙은 글은 타임라인에서 훨씬 눈에 띈다.

`_threads/images/README.md` 의 표에 있는 파일명만 쓴다. 표에 없는 파일은 붙이지 않는다.
초안 JSON에 `"image": "파일명.jpg"` 를 넣으면 워커가 알아서 처리한다.

**붙이지 않아야 할 때**
- 글 내용과 사진이 안 맞을 때. 억지로 붙이면 오히려 신뢰를 깎는다
- 일반론·정보형 글. 케이스 사진을 정보성 글에 붙이면 사례를 과장하는 것처럼 보인다
- 8개 중 사진을 붙이는 건 **2~3개까지**. 매번 붙으면 특별하지 않다

## 말투 규칙

- 짧은 문장, 줄바꿈 충분히
- 경어체 (합니다/입니다)
- 수치는 직접 언급
- 이모지 최소 (행동 촉구 시 1개까지)
- "안녕하세요" 또는 브랜드 소개로 시작 금지
- **해시태그를 쓰지 않는다** (2026-08-11 확정 — 아래)
- 계정 표기는 `@bulk_farmer` (한글 금지)

### 해시태그 금지 — 실측으로 확정 (2026-08-11)

발행된 글과 초안을 전수 대조했다. **초안에 해시태그가 있던 14건 중
`#`를 그대로 둔 글이 0건이다.** 코치가 매번 발행 후 직접 지웠다.

```
# 만 떼고 "벌크업"만 남김   11건
아예 통째로 지움             3건
그대로 둔 것                 0건
```

해시태그가 없던 24건은 손대지 않았다. **없으면 안 고친다.**
그러니 초안에 `#벌크업`을 붙이지 않는다. 끝은 본문 마지막 문장으로 맺는다.

### 첫 줄은 선언이 아니라 현장에서 오간 말이다 (2026-08-05 추가)

읽는 사람을 가르치는 문장으로 열지 않는다. **수업에서 실제로 오간 말**로 연다.

| 쓰지 않는다 | 쓴다 |
|---|---|
| 세 끼로는 부족합니다. | 세 끼는 잘 챙겨드시고<br>계신가요? |
| 보충제 안 먹으면<br>못 크나요? | 선생님, 보충제 먹으면<br>몸이 더 빨리 크나요? |

두 가지 규칙이다.

1. **수강생이 묻는 말은 들은 그대로 쓴다.** 호칭("선생님,")까지 살린다.
   그리고 **실제로 하는 질문**이어야 한다. 사람들은 "안 먹으면 못 크나요"라고
   묻지 않는다. "먹으면 더 빨리 크나요"라고 묻는다. 궁금한 건 결핍이 아니라 효과다.
2. **코치가 여는 말은 확인 질문이다.** "~하고 계신가요?"
   단정("~로는 부족합니다")은 상대가 틀렸다고 먼저 말하는 것이라 방어가 걸린다.

훅을 바꾸면 **본문도 바뀐 질문에 답해야 한다.** 질문이 속도를 물으면
답도 속도로 해야 한다 — "필수가 아닙니다"는 다른 질문의 답이다.

**단, 전부 질문으로 열지 않는다.** 금지 대상은 가르치는 선언이지 평서문이 아니다.

| 종류 | 예 | 판정 |
|---|---|---|
| 가르치는 선언 | 세 끼로는 부족합니다 / 이것 하나만 고치세요 | ✗ |
| 비유·수사 | 인바디는 뒤로 갔는데 줄자는 앞으로 갔다 | ✗ |
| 수강생 행동에 판단 | 그러다 다시 **고쳤습니다** → 다시 **말씀해주셨습니다** | ✗ |
| 본인이 한 일 | 일요일마다 장을 봤습니다 | ✓ |
| 들은 말 인용 | 너는 원래 안 크는 몸이야 | ✓ |
| 확인 질문 | 세 끼는 잘 챙겨드시고 계신가요? | ✓ 남발 금지 |

확인 질문은 **지목형이 아니라 거수형**으로 묻는다.

```
✗  무릎이 안으로 모이지 않으시나요?    한 명을 지목 — 지적당하는 느낌
✓  무릎이 안으로 모이시는 분 계신가요?  해당되는 사람만 걸린다
```

**하루 8개 중 확인 질문은 2개까지.** 나머지는 인용·평서문으로 연다.
구체적인 평서문이 막연한 질문보다 낫다 — "일요일마다"에는 장면이 있고
"미리 사두셨나요?"에는 없다. 질문으로 바꾸느라 장면을 지우면 손해다.

### 압축하지 않는다 · 현장 단어를 쓴다 (2026-08-06 추가)

| ✗ | ✓ | 규칙 |
|---|---|---|
| 무게부터 올리고 싶었습니다 | 무게부터 올리고 싶은 욕심이 있었습니다 | 서술어를 잘라 압축하지 않는다 |
| 숫자만 채웠습니다 | 중량만 올렸습니다 | 헬스장에서 쓰는 말로 |
| 무게를 절반으로 낮추고 | 그 이후, 무게를 다시 낮추고 | 없는 수치를 만들지 않는다 |
| 숫자보다 순서가 먼저입니다 | 중량보다 자세가 먼저입니다 | 결론은 본문 단어로 맺는다 |

**마지막 줄에서 새 단어를 꺼내지 않는다.** 대구를 맞추려고 본문에 없던 추상어
(순서·본질·방향 같은 말)를 끌어오면 글이 겉돈다. 본문에 쓴 명사 두 개로 맺는다.

리스트에 부위를 쓸 때는 "어깨를 넓어 보이게 하는 근육"이 아니라
**측면 삼각근·광배근·삼두근**처럼 실제 이름을 쓴다. 종목도 마찬가지다 —
"큰 근육 운동"이 아니라 **스쿼트·데드리프트**로 적는다.

## 텔레그램 발송

자격증명은 `~/.config/bulkfarmer/telegram.env`. **토큰 값을 출력에 찍지 않는다.**

먼저 요약 1건:
```
📝 오늘의 스레드 초안 N개
3~5개 승인해주세요. 승인하면 100분 간격으로 하나씩 자동 발행됩니다.
```

그다음 초안마다 1건씩, 인라인 버튼을 붙여 보낸다.

```bash
source ~/.config/bulkfarmer/telegram.env
curl -s -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/sendMessage" \
  -H "Content-Type: application/json" \
  -d '{
    "chat_id": CHAT_ID,
    "text": "1/8  유형 1 · B(제한된 믿음)\n\n<본문>",
    "reply_markup": {"inline_keyboard": [[
      {"text":"✅ 발행 예약","callback_data":"pub:YYYY-MM-DD:1"},
      {"text":"🗑 버림","callback_data":"del:YYYY-MM-DD:1"}
    ]]}
  }'
```

`callback_data`는 반드시 `pub:{날짜}:{index}` / `del:{날짜}:{index}` 형식이어야 한다.
워커가 이 형식으로만 파싱한다.

### 사진이 붙는 초안은 사진과 함께 보낸다 (2026-08-11 지시)

`image` 필드가 있는 초안은 `sendMessage`가 아니라 **`sendPhoto`**로 보낸다.
사진을 못 보고 승인하면, 글과 안 맞는 사진이 그대로 나간다.

```bash
curl -s -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/sendPhoto" \
  -F "chat_id=$TELEGRAM_CHAT_ID" \
  -F "photo=@_threads/images/sh_sheet_2month.jpg" \
  -F "caption=5/8  유형 1 · F  📎sh_sheet_2month.jpg

<본문>" \
  -F 'reply_markup={"inline_keyboard":[[{"text":"✅ 발행 예약","callback_data":"pub:2026-08-11:5"},{"text":"🗑 버림","callback_data":"del:2026-08-11:5"}]]}'
```

- **캡션 상한 1,024자.** 스레드 본문은 이 안에 들어가지만 넘으면 사진 따로·글 따로 보낸다
- `sendPhoto` 응답의 `result.message_id`도 똑같이 `sent_msg_id`에 기록한다
- 캡션 첫 줄에 `📎파일명`을 적어 어떤 사진인지 보이게 한다

**글감을 정할 때 사진을 먼저 떠올린다.** `images/README.md`의 표에서 어울리는 컷이
있는 소재라면 그쪽을 우선 고른다 — 사진 붙은 글이 타임라인에서 훨씬 눈에 띈다.
다만 **8개 중 2~3개까지**다. 매번 붙으면 특별하지 않다.

승인은 **즉시 발행이 아니라 예약**이다. 워커가 08~23시 사이에 100분 간격으로
한 건씩 내보낸다. 한꺼번에 눌러도 글이 뭉쳐 나가지 않는다.

버려진 초안이 있으면 마지막에 알린다: "검증에서 N개를 버렸습니다 — 사유: ..."

## 가독성 (모바일 기준으로 쓴다)

**거의 전부 폰으로 본다.** 줄이 길면 읽기 전에 넘긴다. 내용이 좋아도 소용없다.

| 규칙 | 기준 |
|---|---|
| 한 줄 길이 | **12~16자를 목표로.** 상한은 20자지만 목표가 아니다 |
| 첫 줄 | **15자 이내.** 미리보기에서 여기서 승부가 난다 |
| **한 문장** | **1~2줄.** 3줄로 쪼개지 않는다 |
| **한 문단** | **한 문장.** 문장마다 빈 줄을 넣지 말고, 문장 하나가 문단 하나다 |
| 나열 | 반드시 줄바꿈. 쉼표로 이어 쓰지 않는다 |

### 너무 잘게 쪼개지 않는다 (2026-08-06 발행분에서 사용자가 직접 고침)

**짧게 끊는 것과 잘게 부수는 것은 다르다.** 6~8자짜리 줄을 늘어놓으면
읽기 쉬워지는 게 아니라 문장이 안 보인다.

```
✗ 자동 생성 (24줄 · 줄당 평균 6자)
  기구 앞에
  서기만 해도
                    ← 빈 줄
  다들 쳐다보는
  것 같았습니다.

✓ 사용자 수정 (14줄 · 줄당 평균 12자)
  기구 앞에 서기만 해도
  다들 쳐다보는 것 같았습니다.
```

세 가지가 달라졌다.

1. **한 문장을 두 문단으로 나누지 않는다.** 위 예시는 한 문장인데 빈 줄로 갈라놨다
2. **줄을 12~15자로 채운다.** "저도 처음 / 헬스장 갔던 날"이 아니라 "저도 처음 헬스장 갔던 날"
3. **관형절을 끊지 않는다.** "다들 쳐다보는 / 것 같았습니다"는 "것"이 떨어져 어색하다

의미가 안 끊기면 **20자를 넘겨도 한 줄로 둔다.** 사용자가 직접 쓴 예:
`무게부터 올리고 싶은 욕심이 있었습니다.` (22자, 한 줄)

```
✗  자세가 무너진 채로 중량만 늘리다 보니 부상만 남고 근육은 그대로였습니다.   (36자, 폰에서 2~3줄)

✓  자세가 무너진 채로
   중량만 늘리다 보니
   부상만 남고 근육은 그대로였습니다.
```

줄바꿈은 **의미가 끊기는 자리**에 넣는다. 20자를 채우려고 어절 중간을 자르지 않는다.

**저장하기 전에 직접 세어본다.** 각 초안에 대해 아래를 확인하고, 걸리면 고친 뒤 저장한다.

```
한 문장이 3줄 이상으로 쪼개졌는가    → 2줄로 합친다
10자 미만인 줄이 절반을 넘는가       → 너무 잘게 부순 것이다. 합친다
줄 수가 문장 수의 2.5배를 넘는가     → 같은 이유. 합친다
첫 줄이 15자를 넘는가               → 넘으면 줄인다
```

> 2026-08-07 확인: 자동 생성된 초안이 6문장을 **24줄 12문단**으로 부숴놨다.
> 사용자가 발행된 글을 직접 **14줄 6문단**으로 고쳤다. 줄당 6자 → 12자.

> 2026-08-04 확인: 그날 초안의 가장 긴 줄이 67자였고 20자 넘는 줄이 대부분이었다.
> 폰에서 한 문장이 4줄로 접혔다. 사용자가 "가독성 떨어지면 안 읽는다"고 지적했다.

## 발송 검증 (건너뛰지 않는다)

**"보냈습니다"라고 쓰는 것으로 발송이 되지는 않는다.**

초안 하나를 보낼 때마다 응답의 `result.message_id`를 그 초안의 `sent_msg_id`에
적어 넣고 JSON을 저장한다. 응답을 못 받았으면 적지 않는다.

```
발송 → 응답의 message_id 확인 → draft["sent_msg_id"] = message_id → 파일 저장
```

마지막에 **`sent_msg_id`가 없는 초안이 몇 개인지 세어 출력한다.** 0이어야 끝난다.
0이 아니면 그 건들만 다시 보내고, 그래도 안 되면 텔레그램으로 실패를 알린다.

> `msg_id`(밑줄 없는 쪽)와 헷갈리지 않는다. 그건 워커가 **버튼을 눌렀을 때**
> 기록하는 값이라, 없다고 발송 실패인 것이 아니다. 발송 여부는 `sent_msg_id`로만 판단한다.
>
> 2026-08-04에 이 검증이 없어서, 네트워크가 끊긴 동안 돌아간 작업이
> "8개 전부 발송 완료"라고 보고했지만 실제로는 하나도 나가지 않았다.
> 사용자는 어제 메시지의 버튼을 누르고 예약이 된 줄 알고 있었다.

그동안 초안 작성은 해둬도 되지만 **발송은 연결이 확인된 뒤에 한다.**
